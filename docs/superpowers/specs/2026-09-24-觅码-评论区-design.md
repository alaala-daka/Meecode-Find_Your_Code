## 1. 背景与目标

仓库页 `RepoPage.tsx:222-229` 目前是 giscus 占位文案（「评论区（giscus，后端就绪后接入）」），后端 `discussions_open` 探测（`repos.py` 的 `github.get_discussion_meta`）只为这个占位服务。路线图把评论区列为第二批、定位为**一切 UGC 的数据底**——第三批管理端的评论过滤、第四批作者回复提醒都挂 `comments` 表，必须先行。

本批交付自托管评论区（替换 giscus 占位）：

1. **数据底**：`comments` 表（两层平铺：顶层 + 回复），状态机 `pending → visible / hidden / deleted`；
2. **LLM 异步预审**：每条评论必经 LLM 合规审查——入库 `pending` 即返回，后台判定后转 `visible`/`hidden`，POST 不阻塞；
3. **权限最小集**：登录用户发表/软删自己；作者/认领者隐藏本仓库任意评论；管理员能力留给第三批；
4. **安全衔接**：新端点进 `security.py` 分桶（新桶 `ugc`）、渲染 sanitize 白名单与 README 一致（单点审计）、移动端按移动优先建造。

**非目标（YAGNI）**：
- 无限嵌套回复（两层平铺封顶）；
- 评论编辑（只软删，防「发后改内容」争议）；
- 评论点赞/置顶/排序切换（固定 `created_at ASC`）；
- 举报按钮与管理端（第三批）；
- 验证码（维持安全基线 spec「评论区上线后再按需评估」的约定）；
- LLM 用量记账（路线图列为第三批独立 Task；本批成本敞口见风险表）；
- giscus / GitHub Discussions 兼容或数据迁移（现占位从未产生真实评论）。

## 4. 详细设计

### 4.1 数据模型（`backend/app/feed/db.py`）

```sql
CREATE TABLE IF NOT EXISTS comments (
    id          INTEGER PRIMARY KEY,
    repo_id     INTEGER NOT NULL REFERENCES repos(id),
    user_id     INTEGER NOT NULL REFERENCES users(id),
    parent_id   INTEGER REFERENCES comments(id),  -- NULL=顶层；非 NULL 时恒指顶层
    content     TEXT    NOT NULL,
    status      TEXT    NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','visible','hidden','deleted')),
    screened    INTEGER NOT NULL DEFAULT 0,       -- 0=LLM 尚未判定（含失败待重试）；1=已判定
    moderation_reason TEXT NOT NULL DEFAULT '',   -- LLM 拒绝原因（空=通过/作者隐藏，2026-09-25 补）
    created_at  INTEGER NOT NULL DEFAULT (unixepoch())
);
CREATE INDEX IF NOT EXISTS idx_comments_repo     ON comments (repo_id, status, created_at);
CREATE INDEX IF NOT EXISTS idx_comments_parent   ON comments (parent_id, created_at);
CREATE INDEX IF NOT EXISTS idx_comments_unscreen ON comments (screened, created_at);
```

状态流转（本批实线；第三批虚线由其 spec 定）：

```
pending ──LLM 合规──> visible ──作者/本人/管理──> hidden / deleted
   │                     │
   │──LLM 违规──> hidden ┘（管理端第三批可恢复 visible）
   └──LLM 异常──不动，重试 job 扫 screened=0
pending（举报流，第三批）… 管理员 → visible / hidden / deleted
```

- 沿用库惯例：INTEGER PK、`unixepoch()` 时间戳、TEXT + CHECK 枚举。`moderation_reason` 为 2026-09-25 上线后补列，`init_db` 走 `PRAGMA table_info` + ALTER 轻量迁移（session_epoch 同款），**补列同事务把存量 `hidden` 行重置 `pending, screened=0` 一次性重审**（旧口径误杀的恢复手段；作者手动隐藏的也重审，测试期样本可接受）；
- `screened` 复刻 `repos.screened` 语义（0=LLM 精筛未完成），重试任务对齐 `crawl.rescreen_pending` 形态；
- 不存 `edited_at` / `hidden_by`（无编辑；隐藏来源字段留第三批按需 ALTER）。

### 4.2 API（`backend/app/feed/routes/comments.py`，挂 `prefix="/api"`）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/comments?repo_id=&limit=20&offset=0` | 公开 | 平铺列表，`created_at ASC`，`{items, total}` |
| POST | `/comments` | 登录 | `{repo_id, content, parent_id?}` → 返回创建行（`status='pending'`） |
| DELETE | `/comments/{id}` | 登录 | 软删自己的（`status='deleted'`，**级联软删其回复**），非本人 403 |
| POST | `/comments/{id}/hide` | 登录 | 作者/认领者隐藏（`status='hidden'`），无权限 403 |

**路径扁平（决策 9）**：写端点统一挂 `/api/comments`（`repo_id` 进 body/query），与 `POST /api/interactions` 同款惯例——`POST /api/repos/{id}/comments` 与 delist 桶共享前缀 `/api/repos/` 且差异在路径尾段，限流规则的前缀匹配无法靠排序区分。

**分页语义**：`limit/offset` 的分页对象为**顶层线程**（线程不跨页）；`items` 仍为平铺数组（每个顶层后跟其全部可见回复，`created_at ASC`）；`total` 为顶层线程数。

规则：

- `content`：strip 后非空、≤ `config.COMMENT_MAX_LEN`（默认 2000），否则 422（中文文案）；
- `parent_id`：给定时须存在于同仓库；若指向回复，**归一**为其顶层祖先（两层平铺，宽容实现防前端漏网）；不存在 / 跨仓库 → 422「回复的父评论不存在」；直接父或归一后顶层为 `hidden`/`deleted` → 422「不能回复已隐藏或已删除的评论」（决策 12，作者本人也不例外）；
- 目标仓库须未下架（`status != 'delisted'`），否则 404「仓库不存在或已下架」——与浏览/点赞同口径（`pending_claim` 采集仓库可看可赞，评论不得掉队）；2026-09-24 联调修复：原写 `status='published'` 会把采集仓库挡在评论外；
- 作者判定：`repos.claimed_by == user.id OR repos.owner_login == user.login`（与 `submit.py:180` delist 权限同口径）；
- GET 可见性：`status='visible'` 全员可见 + 请求者**本人**的 `pending`/`hidden`（响应含 `status` 字段供前端渲染「审核中 / 未通过」标记）；`deleted` 永不返回；他人 `pending`/`hidden` 不返回；
- `CommentOut`：`{id, repo_id, user_id, user_login, user_avatar, parent_id, content, status, created_at, created_at_iso}`（`cards.py` 的 `_iso` 同款）；
- 沿用 `auth.require_user` / `deps.get_conn` / `HTTPException(中文)` 既有风格。

**退役项**：`RepoDetailOut.discussions_open` 字段删除；`get_repo` 中 `github.get_discussion_meta` 探测块删除；`github.get_discussion_meta` 函数及 `test_repos.py` 相关用例删除；`frontend/src/api/types.ts` 的 `RepoDetail.discussions_open` 同步删除。

### 4.3 LLM 异步预审（`backend/app/feed/moderation.py`）

复用 `feed/llm.py` 的 `chat_json`（JSON mode + Pydantic 校验重试一次）：

```python
class CommentVerdict(BaseModel):
    is_compliant: bool
    reason: str          # 简体中文，不超过 30 字
```

Prompt 口径（决策 8）：

- system：中文社区评论审核员；广告导流、人身攻击、辱骂仇恨、色情赌博等违法信息、无意义刷屏灌水 → 不合规；**技术提问、意见批评、代码相关讨论（即使尖锐）一律合规**；只输出 JSON `{"is_compliant": bool, "reason": "..."}`；
- user：评论正文（截断至 2000 字符）。

`moderate_comment(conn, comment_id)`：

1. 读行（不存在/已 `deleted` 则直接返回）；
2. `config.LLM_MOCK` → `mock.mock_comment_verdict(content)`（确定性：含「垃圾」「广告」等词 → 不合规）；否则 `llm.chat_json(...)`；
3. 合规 → `UPDATE comments SET status='visible', screened=1, moderation_reason=''`；违规 → `status='hidden', screened=1` 并把判定原因写入 `moderation_reason`（内容保留，决策 2；原因仅拒绝时非空——徽标据此区分「未通过审核」与「作者/管理隐藏」，2026-09-25 上线修订补）；违规级联：其回复一并 `hidden`（不写原因，决策 12）；
4. 任何异常（超时/解析失败）→ 不落库，保持 `pending, screened=0` 由重试 job 兜底；判定结果打 `[moderate]` 日志（含原因）供运维诊断。

触发：`POST /comments` 事务提交后经 FastAPI `BackgroundTasks` 调度 `moderate_comment`（响应不等 LLM）。

### 4.5 限流分桶（`backend/app/security.py` + `backend/app/config.py`）


### 4.7 交互流程（用户视角）

1. 登录用户在仓库页输入评论 → 发送 → 立刻看到「审核中」的自己评论（他人暂不可见）；
2. 数秒后 LLM 判定通过 → 全员可见；判定不通过 → 作者侧显示「未通过」（内容仅作者与管理员可见）。状态由前端 3s 轮询自动落到徽标，**无需手动刷新**（决策 13）；
3. 读者对顶层/回复点「回复」→ 内嵌框 → 同样入 `pending` 流程；
4. 作者在自己仓库下点「隐藏」→ 对全员立即不可见（**其回复一并隐藏**，决策 12）；评论者本人 GET 仍返回该行并带「已隐藏」标记（与 LLM 判 `hidden` 同状态，不暴露隐藏来源）；
5. 误发点「删除」→ 软删（**其回复一并软删**，决策 12），列表消失，永不返回；被隐藏/已删除的评论不再有「回复」入口。

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 每条评论 1 次 LLM 调用，用量无记账 → 成本不可见 | `ugc` 桶 10/min 封顶（决策 9）；记账显式推第三批（决策 10）；本条留档供第三批 spec 引用 |
| LLM 误杀正常技术讨论 | Prompt 明确「尖锐批评/代码讨论一律合规」（决策 8）；`hidden` 保留内容，第三批管理端可恢复 |
| LLM 故障时评论堆积 `pending`，用户以为丢评 | 作者侧「审核中」标记可见；重试 job + runbook cron 兜底；不做自动降级放行（预审语义要求 fail-closed） |
| `POST /api/comments` 若误挂嵌套路径会撞 delist 前缀桶 → 限流失效 | 决策 9 扁平化根治（前缀不相交）；`bucket_for` 断言用例含 delist 回归 |
| 推翻 2026-08-24 spec 的 giscus 决策引发认知冲突 | 决策记录表第 1 条留痕：自托管是 UGC 数据底的必然（管理过滤/回复通知挂点），路线图已定调 |
| 评论 markdown 渲染面（存储型 XSS） | 白名单与 README 完全一致并抽共享模块（决策 6），安全基线已审过的 schema 不重新发明 |
